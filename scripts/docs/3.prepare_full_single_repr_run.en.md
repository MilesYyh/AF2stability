# 3.prepare_full_single_repr_run.py

## Role in the pipeline

This script formalizes large-scale AF2 execution. It does **not** run AlphaFold directly. Instead, it reads the full manifest, generates a 4-GPU shell runner, and writes a run summary.

So conceptually it is a batch-run orchestrator rather than the inference engine itself.

---

## What problem it solves

Once the project scales to thousands of samples, hand-writing `run_docker.py` commands becomes fragile and unmaintainable. This script centralizes the following responsibilities:

- read the full AF2 manifest
- expand WT and mutant tasks correctly
- ensure WT tasks are generated only once per protein
- generate a 4-way GPU-dispatch shell runner
- always enable `--save_single_representation=true`
- skip tasks that already completed successfully

---

## Inputs and outputs

### Input

- default input: `data/manifests/fireprotdb_phase1_af2_manifest.csv`

### Outputs

- runner script: `results/af2/single-repr-full/run_single_repr_full.sh`
- run summary: `results/af2/single-repr-full/summary.json`
- intended output directory: `results/af2/single-repr-full/outputs/`
- intended log directory: `results/af2/single-repr-full/logs/`

Important: this script prepares the execution layer. The generated shell script performs the actual AF2 run.

## How the code is organized

### 1. Version marker and helpers

- `VERSION`
- `shell_quote()`
  - quotes shell strings safely
- `resolve_repo_path()`
  - resolves repository-relative paths
- `load_manifest_rows()`
  - loads the full manifest table
- `build_tasks()`
  - converts manifest rows into AF2 execution tasks
- `write_summary()`
- `build_summary()`

### 2. Why `build_tasks()` matters

Each manifest row represents one mutation sample, but the AF2 workload is:

- one WT run per protein
- one mutant run per sample

Therefore, the total AF2 task count is not equal to the number of manifest rows.

The script uses `seen_wt` to guarantee that each WT sequence is scheduled only once.

### 3. `main()`

`main()` does the following:

1. parse CLI arguments
2. resolve all important paths
3. load the manifest
4. construct the AF2 task list
5. enforce a 4-GPU configuration
6. generate the shell runner text
7. write the runner and summary

---

## How the generated shell runner works

The runner expands all tasks into shell variables such as:

- `FASTA_i`
- `NAME_i`
- `TASKID_i`

Then it defines a `run_gpu(gpu, offset)` function and dispatches tasks using a fixed-stride loop:

```bash
for ((i=offset; i<TASK_COUNT; i+=GPU_COUNT)); do
```

Example:

- GPU0 runs tasks 0, 4, 8, 12, ...
- GPU1 runs tasks 1, 5, 9, 13, ...
- GPU2 runs tasks 2, 6, 10, 14, ...
- GPU3 runs tasks 3, 7, 11, 15, ...

This is a simple and robust cyclic dispatch policy.

---

## Completion and skip logic

The generated runner uses this condition:

```bash
if [ -f "$outdir/single_repr_model_1_pred_0.npy" ]; then
  skip
fi
```

That means the operational definition of “done” is:

- the target already has a dumped single representation

This is more aligned with the downstream pipeline than checking only for `ranked_0.pdb`, because the next stages depend on the `.npy` representation file.

---

## Why the script enables single-representation output directly

The current project is no longer just about structure prediction. It is about structure prediction plus internal-representation extraction.

The generated runner therefore always includes:

- `--save_single_representation=true`
- `--run_alphafold_source_path=alphafold2/run_alphafold.py`

This means it depends on the locally modified AlphaFold entrypoint rather than a fully stock upstream runner.

## How to run it

### Step 1: generate the full-run runner

```bash
python scripts/3.prepare_full_single_repr_run.py
```

### Step 2: execute the generated full run

```bash
bash results/af2/single-repr-full/run_single_repr_full.sh
```

### Explicit example

```bash
python scripts/3.prepare_full_single_repr_run.py \
  --input-manifest data/manifests/fireprotdb_phase1_af2_manifest.csv \
  --gpu-ids 0,1,2,3 \
  --data-dir /data/AFDB \
  --output-dir results/af2/single-repr-full/outputs \
  --log-dir results/af2/single-repr-full/logs \
  --runner-script results/af2/single-repr-full/run_single_repr_full.sh \
  --summary-json results/af2/single-repr-full/summary.json
```

## What to inspect before and after running

### Before running

Check:

1. `summary.json` reports a sensible `total_tasks`
2. `gpu_ids` really represent the intended four devices
3. `run_script` and `run_alphafold_source_path` point to the current repository copy

### During or after running

Check:

1. `outputs/<target>/single_repr_model_1_pred_0.npy` appears over time
2. `logs/*.log` are actively growing
3. the run is not stalled for too long on extremely long proteins

---

## Common pitfalls

### 1. This script does not launch the run by itself

It prepares the runner. You still need to execute the generated shell script.

### 2. It currently enforces exactly four GPUs

If your environment is not 4-GPU, the script will stop with an error.

### 3. It depends on the local modified `run_alphafold.py`

If that file is replaced or reset, single-representation dumping may stop working.

### 4. Skip logic depends on `.npy`, not only on structure files

If a target produced a structure but not `single_repr_model_1_pred_0.npy`, it will still be treated as incomplete.

## Natural extension points

Good future extensions include:

- priority scheduling or sequence-length bucketing
- progress snapshot generation
