# 1.prepare_fireprotdb_phase1_dataset.py

## Role in the pipeline

This is the first script in the AF2stab mainline workflow. Its job is to convert the raw FireProtDB-derived CSV table in `dataset/fireprotdb_results.csv` into a phase-1 mutation dataset that can be consumed safely by downstream FASTA generation, AlphaFold inference, feature extraction, and ddG training.

The script is intentionally conservative. It prefers producing a smaller but structurally valid dataset over carrying forward noisy or ambiguous records.

---

## What problem this script solves

The raw FireProtDB result table may contain records that are unsuitable for the later pipeline stages, for example:

- missing or invalid `ddG`
- missing sequences
- non-standard residues in the sequence
- invalid or out-of-range mutation positions
- WT residue inconsistent with the sequence at the reported position
- missing stable protein identifiers
- repeated experimental records for the same mutation

If these issues are not removed here, later failures become much harder to diagnose because the error could appear during FASTA generation, AF2 execution, representation extraction, or MLP training.

---

## Inputs and outputs

### Input

- default input: `dataset/fireprotdb_results.csv`

The script operates directly on the CSV table and does not require the SQL dump.

### Outputs

- `data/processed/fireprotdb_phase1_ddg_clean.csv`
- `data/processed/fireprotdb_phase1_ddg_summary.json`

The CSV is the canonical downstream dataset. The JSON summary is the audit trail describing how the final dataset was derived.

---

## How the code is structured

The script follows a compact ETL-style organization.

### 1. Top-level constants and type definitions

- `STANDARD_AA`
  - the allowed 20 standard amino acids
- `MutationRecord`
  - a `TypedDict` describing the validated intermediate record

This makes the accepted data model explicit at the top of the file.

### 2. Small helper functions

- `apply_mutation()`
  - constructs the mutant sequence from a WT sequence and a 1-based mutation site
- `clean_str()`
  - normalizes empty values and strips whitespace
- `normalize_sequence()`
  - uppercases and removes spaces
- `normalize_pdb_id()`
  - canonicalizes raw PDB identifiers
- `is_standard_residue()`
  - validates one-letter amino-acid codes
- `make_sequence_hash()`
  - creates a short stable sequence hash

These helpers keep the record-processing loop readable and make normalization rules consistent.

### 3. `parse_args()`

Defines the CLI interface:

- input CSV path
- clean output CSV path
- summary JSON path

### 4. `main()`

`main()` performs the full ETL pass:

1. read the raw CSV
2. validate and filter each row
3. group duplicate experiments by mutation key
4. collapse duplicates using median ddG
5. write the clean table and the summary report

---

## Core filtering logic

Each row must pass all of the following checks:

1. `ddG` must be present and parseable as a finite float
2. `sequence` must be present
3. the sequence must contain only standard amino acids
4. `position` must be present, integer, and within sequence bounds
5. `wild_type` and `mutation` must both be one-letter standard residues
6. `wild_type != mutation`
7. the sequence residue at `position` must match `wild_type`
8. a stable `protein_id` must be derivable

### `protein_id` priority rule

The script defines protein identity using the following precedence:

1. use `uniprot_id` when present
2. otherwise use `normalized_pdb_id + '_' + chain`

This matters because the mutation grouping key depends on protein identity.

---

## How duplicate experiments are merged

Validated rows are grouped by:

- `(protein_id, position, wild_type, mutation)`

This means multiple experimental measurements for the same mutation are collapsed into one training sample.

During collapse:

- `median_ddg` is computed from all duplicate measurements
- `num_experiments` stores the duplicate count
- experiment IDs, raw ddG values, DOIs, and PubMed IDs are retained for traceability

---

## Important output columns

The clean CSV includes, among others:

- `protein_id`
- `position`
- `wild_type`
- `mutation`
- `mutation_label`
- `median_ddg`
- `num_experiments`
- `wild_type_sequence`
- `mutant_sequence`
- `sequence_length`

The mutant sequence is reconstructed by the script rather than trusted blindly from the raw table.

---

## What the summary JSON is for

`fireprotdb_phase1_ddg_summary.json` is an audit artifact. It explains why the final dataset has the size it has.

It records:

- total input row count
- number of rows with valid ddG
- number of rows surviving phase-1 filters
- final unique mutation count after duplicate collapse
- exclusion reason counts
- missing identifier counts
- duplicate-group size distribution

This file is essential for data provenance.

## How to run it

### Default usage

```bash
python scripts/1.prepare_fireprotdb_phase1_dataset.py
```

### Explicit paths

```bash
python scripts/1.prepare_fireprotdb_phase1_dataset.py \
  --input dataset/fireprotdb_results.csv \
  --output-csv data/processed/fireprotdb_phase1_ddg_clean.csv \
  --output-summary data/processed/fireprotdb_phase1_ddg_summary.json
```

---

## What to check after running

At minimum, verify:

1. the clean CSV exists
2. the summary JSON exists
3. the final unique mutation count is in the expected range
4. exclusion reasons such as `wild_type_sequence_mismatch` are not unexpectedly large

If one exclusion category spikes, the input schema or semantics may have changed.

---

## Common pitfalls

### 1. Positions are biologically 1-based

The script converts to 0-based indexing only when slicing Python strings.

### 2. Raw PDB IDs are not always canonical

They are normalized before use and should not be concatenated directly without cleaning.

### 3. `mutation_label` is derived

It is constructed by the script from WT residue, site, and mutant residue.

### 4. Filtering and auditing are coupled

If you change the filtering rules, the meaning of the summary statistics changes too.

## Position in the overall workflow

This script sits at the start of the full pipeline:

1. `1.prepare_fireprotdb_phase1_dataset.py`
2. `2.build_mutant_fastas.py`
3. `3.prepare_full_single_repr_run.py`
4. `4.extract_single_repr_features.py`
5. `5.train_ddg_mlp.py`

If the dataset definition is unstable here, every later stage inherits that instability.

---

## Natural extension points

This script is the right place to extend the pipeline toward a stricter paper-like reproduction, for example:

- tighter dataset inclusion rules
- explicit `ΔΔTm` handling
- extra homology-related metadata columns
- split-group metadata for residue-based or homology-aware CV

So while it is a cleaning script, it also acts as the data-definition layer of the whole project.
