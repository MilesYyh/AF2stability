# 2.build_mutant_fastas.py

## 脚本定位

这个脚本承接 phase-1 清洗结果，把结构化的突变表转换成后续 AlphaFold 批量运行真正需要的两类文件：

1. WT FASTA 文件
2. mutant FASTA 文件

同时它会生成全量 AF2 manifest，作为后续结构预测、特征抽取和训练阶段的核心索引表。

---

## 这个脚本有什么用

前一个脚本产出的 `fireprotdb_phase1_ddg_clean.csv` 仍然只是“表格数据”。

AlphaFold 运行不需要表格，而需要：

- 每个目标序列对应的 `.fasta`
- 一个能把 `sample_id / protein_id / ddG / fasta 路径` 关联起来的清单文件

这个脚本就是把“训练样本表”转换成“推理输入资产 + 清单”的桥梁。

---

## 输入与输出

### 输入

- 默认输入：`data/processed/fireprotdb_phase1_ddg_clean.csv`

### 输出

- WT FASTA 目录：`data/interim/fasta/wild_type/`
- mutant FASTA 目录：`data/interim/fasta/mutant/`
- manifest：`data/manifests/fireprotdb_phase1_af2_manifest.csv`
- summary：`data/manifests/fireprotdb_phase1_af2_manifest_summary.json`

---

## 代码是怎么写的

这个脚本采用了比较清晰的“helper + orchestration”组织方式。

### 1. 顶部常量

- `VERSION = '1.0.0'`

用于在输出 summary 中记录脚本版本。

### 2. 小型 helper

- `wrap_fasta_sequence()`
  - 把长序列按固定宽度换行，生成规范 FASTA 正文
- `write_fasta()`
  - 写单个 FASTA 文件
- `resolve_repo_path()`
  - 把相对路径统一解析到仓库根目录下
- `load_clean_rows()`
  - 读取 clean.csv
- `build_manifest_rows()`
  - 真正的核心函数，负责：
    - 生成 WT / mutant FASTA
    - 组装 manifest 行
- `write_csv_rows()`
  - 写 manifest CSV
- `write_summary()`
  - 写 JSON summary
- `build_summary()`
  - 汇总统计信息

### 3. `main()`

`main()` 只负责调度：

1. 解析路径参数
2. 读取 clean rows
3. 生成 FASTA 和 manifest rows
4. 写 CSV
5. 写 summary

这让主流程很短，也便于以后把逻辑拆到模块里。

---

## FASTA 是怎么生成的

### WT FASTA

对同一个 `protein_id`，只会写一次 WT FASTA：

- 文件名：`{protein_id}.fasta`
- header：`>{protein_id}`

因为同一个蛋白可能对应很多不同突变样本，但 WT 序列本身只需要一份。

### mutant FASTA

每个突变样本都会写一个 mutant FASTA：

- 文件名：`{protein_id}__{mutation_label}.fasta`
- header：`>{mutation_id}`

也就是说 mutant 文件是按样本一一展开的。

---

## manifest 里写了什么

输出的 `fireprotdb_phase1_af2_manifest.csv` 是整个主流程的枢纽。

它至少记录：

- `sample_index`
- `sample_id`
- `protein_id`
- `mutation_label`
- `position`
- `wild_type`
- `mutation`
- `median_ddg`
- `num_experiments`
- `sequence_length`
- `wt_fasta_path`
- `mutant_fasta_path`
- `wt_sequence`
- `mutant_sequence`

后面的 AF2 运行、特征抽取和训练都依赖这个表来追踪样本。

---

## 为什么这个 manifest 很重要

它的作用不只是“记录路径”，而是建立整个流程的样本主键体系。

比如：

- AF2 输出目录名依赖 `protein_id` 或 `sample_id`
- 特征抽取要靠 `sample_id` 和 `protein_id` 去找 WT / mutant representation
- 训练阶段要把 `sample_id` 和 `ddG` 对上

如果 manifest 命名混乱，后面就会出现标签错配、找不到文件、重复运行等问题。

## 如何运行

### 默认运行

```bash
python scripts/2.build_mutant_fastas.py
```

### 显式指定路径

```bash
python scripts/2.build_mutant_fastas.py \
  --input-csv data/processed/fireprotdb_phase1_ddg_clean.csv \
  --wt-dir data/interim/fasta/wild_type \
  --mutant-dir data/interim/fasta/mutant \
  --manifest-csv data/manifests/fireprotdb_phase1_af2_manifest.csv \
  --summary-json data/manifests/fireprotdb_phase1_af2_manifest_summary.json
```

---

## 运行后要检查什么

建议至少检查：

1. `data/interim/fasta/wild_type/` 是否生成 WT FASTA
2. `data/interim/fasta/mutant/` 是否生成 mutant FASTA
3. `data/manifests/fireprotdb_phase1_af2_manifest.csv` 是否存在
4. summary 里的：
   - `unique_wt_fastas`
   - `unique_mutant_fastas`
   - `manifest_rows`

这些统计能快速反映“是否所有样本都被正常展开”。

## 常见坑

### 1. 不要把 WT FASTA 按样本重复写

脚本当前逻辑是同一 `protein_id` 只写一次 WT FASTA，这个设计是对的，不要改成一条样本一份 WT 文件。

### 2. 路径解析基于仓库根目录

脚本使用 `Path.cwd()` + 相对路径，因此最好在仓库根目录运行。

### 3. `sample_id` 是后续最重要的样本键

manifest 里真正代表“一个突变样本”的字段是 `sample_id`，不要只看 `mutation_label`。

### 4. 这个脚本不重新验证突变合法性

它相信上一步 `clean.csv` 已经过滤干净，所以前一步出错会一路传下来。
