# 1.prepare_fireprotdb_phase1_dataset.py

## 脚本定位

这是 AF2stab 主流程的第一个脚本，用来把 `dataset/fireprotdb_results.csv` 里的原始 FireProtDB 导出表清洗成一个可以直接进入后续 WT/mutant FASTA 构建流程的 phase-1 数据集。

它的核心目标不是“尽量保留所有记录”，而是“尽量保留后续 AlphaFold 和特征提取一定能消费的记录”。因此它做了比较严格的过滤、校验和重复实验合并。

---

## 这个脚本解决什么问题

原始 FireProtDB 结果表里存在以下典型问题：

- `ddG` 缺失或不是有效数值
- `sequence` 缺失，或者包含非标准氨基酸字符
- `position` 为空、越界、不是整数
- `wild_type` 与给定序列该位点的残基不一致
- 缺少稳定的蛋白标识符
- 同一个突变有多条实验记录，需要折叠成一个训练样本

如果不先做这一步，后面的 FASTA 生成、AF2 运行、位点向量提取都会混入坏样本，最后很难定位问题到底来自数据、推理还是训练阶段。

---

## 输入与输出

### 输入

- 默认输入：`dataset/fireprotdb_results.csv`

这是一张已经从 FireProtDB 整理出来的 CSV 表，脚本只依赖 CSV，不依赖 SQL dump。

### 输出

- `data/processed/fireprotdb_phase1_ddg_clean.csv`
- `data/processed/fireprotdb_phase1_ddg_summary.json`

其中：

- `clean.csv` 是后续主流程真正使用的数据表
- `summary.json` 是审计记录，告诉你总行数、过滤原因、重复合并情况等

---

## 代码是怎么组织的

这个脚本的写法是典型的“主逻辑 + 小型 helper 函数”结构。

### 1. 顶部常量与类型

- `STANDARD_AA`
  - 定义允许出现的 20 种标准氨基酸字符
- `MutationRecord`
  - 用 `TypedDict` 描述单条通过过滤的中间记录结构

这一层的作用是把“什么样的数据是合法的”写死在代码最前面，避免后面遍历时逻辑分散。

### 2. 小型纯函数 helper

- `apply_mutation(sequence, position, mutation)`
  - 根据 1-based 位点生成 mutant 序列
- `clean_str()`
  - 清理空值与首尾空白
- `normalize_sequence()`
  - 序列大写化并移除空格
- `normalize_pdb_id()`
  - 把原始 `pdb_id` 规整成统一形式
- `is_standard_residue()`
  - 判断单字符是否为标准氨基酸
- `make_sequence_hash()`
  - 用 SHA1 前 12 位给序列做稳定 hash

这些函数有两个作用：

1. 让主循环可读，不把各种字符串处理揉成一坨
2. 让同一类规范化规则始终保持一致

### 3. `parse_args()`

负责定义命令行参数。当前参数不多，只有输入路径和两个输出路径。

### 4. `main()`

`main()` 里完成三件大事：

1. **遍历原始 CSV 并做逐行过滤**
2. **按突变键聚合重复实验**
3. **写出 clean.csv 与 summary.json**

这是典型的 ETL 风格脚本：

- Extract：读原始 FireProtDB CSV
- Transform：过滤、归一化、聚合、生成 mutant sequence
- Load：写出后续流程消费的数据表

---

## 关键过滤逻辑

逐行过滤时主要检查以下条件：

1. `ddG` 必须存在，且能解析为有限浮点数
2. `sequence` 必须存在
3. 序列必须全部是标准氨基酸字符
4. `position` 必须存在、能转整数、且落在序列长度范围内
5. `wild_type` 和 `mutation` 都必须是单字符标准氨基酸
6. `wild_type != mutation`
7. `sequence[position - 1]` 必须等于 `wild_type`
8. 必须能构造出稳定的 `protein_id`

### `protein_id` 的构造规则

优先级如下：

1. 如果有 `uniprot_id`，直接用它
2. 否则退化到 `PDB_ID + chain`

也就是：

- `uniprot_id` 优先
- 否则使用 `normalized_pdb_id + '_' + chain`

这个选择很重要，因为它决定了“同一个蛋白”的样本如何归组。

---

## 重复实验是怎么合并的

过滤通过后，脚本不会立刻写出样本，而是先按以下 key 聚合：

- `(protein_id, position, wild_type, mutation)`

也就是把“同一蛋白、同一位点、同一氨基酸替换”的多条实验记录折叠成一个样本。

合并时：

- `median_ddg` 用所有重复记录的中位数
- `num_experiments` 记录这个突变对应多少条实验
- `experiment_ids` / `ddg_values` / `publication_dois` / `publication_pubmeds` 都会保留到输出里，方便审计

---

## 输出表里有哪些关键列

`fireprotdb_phase1_ddg_clean.csv` 里最关键的是：

- `protein_id`
- `position`
- `wild_type`
- `mutation`
- `mutation_label`
- `median_ddg`
- `num_experiments`
- `wild_type_sequence`
- `mutant_sequence`
- `sequence_length`

这里的 `mutant_sequence` 不是从原始数据直接相信，而是脚本基于 WT 序列和位点替换重新构造出来的。

---

## summary.json 有什么用

`fireprotdb_phase1_ddg_summary.json` 主要是用来回答“为什么最后只剩这些样本”的。

它包含：

- 总输入行数
- 有效 `ddG` 行数
- 过滤后剩余行数
- 重复合并后的唯一突变数
- 各种排除原因统计
- 缺失 identifier 的统计
- 重复组大小分布

这是数据阶段非常重要的可追踪性输出。

```bash

  --input dataset/fireprotdb_results.csv \

  --output-summary data/processed/fireprotdb_phase1_ddg_summary.json
```

## 运行成功后应该检查什么

至少检查这几项：

1. `data/processed/fireprotdb_phase1_ddg_clean.csv` 是否生成
2. `data/processed/fireprotdb_phase1_ddg_summary.json` 是否生成
3. `unique_mutations_after_collapse` 是否在预期量级
4. `wild_type_sequence_mismatch` 这类排除原因是否异常高

如果某类排除原因突然很多，往往说明原始 CSV 字段格式变了。

---

## 常见坑

### 1. 位点编号是 1-based

脚本内部在访问字符串时会转成 Python 的 0-based 索引，但逻辑定义是按 1-based 位点写的。

### 2. 原始 `pdb_id` 可能带额外符号

所以要经过 `normalize_pdb_id()`，不能直接拿原字段拼接。

### 3. `mutation_label` 是派生字段

它不是输入列，而是脚本根据 `wild_type + position + mutation` 重新构造的。

### 4. 数据集审计和主表写出是耦合的

如果你改过滤逻辑，`summary.json` 的统计也会跟着变化，不能只盯最终样本数。
