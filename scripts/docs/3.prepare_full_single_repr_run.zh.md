# 3.prepare_full_single_repr_run.py

## 脚本定位

这是把 AF2 批量运行“正式化”的脚本。它本身**不直接运行 AlphaFold 预测**，而是根据全量 manifest 生成一个可以在 4 张 GPU 上并行执行的 shell runner，并输出一份运行 summary。

所以它更像“批处理运行编排器”，而不是推理核心。

---

## 它解决什么问题

当样本数量扩展到几千条时，手工拼 `run_docker.py` 命令已经不可维护。这个脚本把下面这些事情统一收拢：

- 从 manifest 读取全部 WT / mutant 任务
- 自动保证 WT 任务只跑一次
- 自动展开 mutant 任务
- 生成 4 卡轮转分发的 runner 脚本
- 自动带上 `--save_single_representation=true`
- 自动跳过已经完成的任务

---

## 输入与输出

### 输入

- 默认输入：`data/manifests/fireprotdb_phase1_af2_manifest.csv`

### 输出

- runner：`results/af2/single-repr-full/run_single_repr_full.sh`
- summary：`results/af2/single-repr-full/summary.json`
- 运行目标输出目录：`results/af2/single-repr-full/outputs/`
- 日志目录：`results/af2/single-repr-full/logs/`

注意：脚本生成的是“运行脚本”和“运行配置”，真正执行预测的是生成出来的 shell 脚本。

---

## 代码是怎么写的

### 1. 顶部常量与 helper

- `VERSION`
- `shell_quote()`
  - 统一做 shell 转义，避免路径里特殊字符出问题
- `resolve_repo_path()`
  - 相对路径统一挂到仓库根目录
- `load_manifest_rows()`
  - 读取全量 manifest
- `build_tasks()`
  - 最重要的逻辑之一：把 manifest 转成 AF2 任务列表
- `write_summary()`
- `build_summary()`

### 2. `build_tasks()` 的意义

manifest 的每一行对应一个突变样本，但 AF2 真正要跑的是：

- 每个蛋白一个 WT
- 每个样本一个 mutant

所以任务总数并不等于 manifest 行数，而是：

- `unique_wt_sequences + mutant_samples`

脚本用 `seen_wt` 保证同一 `protein_id` 的 WT 只加入一次任务队列。

### 3. `main()`

`main()` 做的事：

1. 解析参数
2. 读 manifest
3. 构建任务列表
4. 检查 GPU id 数量是否为 4
5. 生成 shell runner 文本
6. 写 runner
7. 写 summary

---

## 生成出来的 shell runner 是怎么工作的

runner 的核心逻辑是：

- 把所有任务展开成 `FASTA_i / NAME_i / TASKID_i`
- 定义 `run_gpu(gpu, offset)` 函数
- 每张卡按 `i = offset; i < TASK_COUNT; i += GPU_COUNT` 的方式取任务

这是一种固定步长轮转调度方式。

举例：

- GPU0 处理任务 0,4,8,12...
- GPU1 处理任务 1,5,9,13...
- GPU2 处理任务 2,6,10,14...
- GPU3 处理任务 3,7,11,15...

优点是简单、稳定、容易恢复。

---

## 跳过逻辑是怎么设计的

runner 会检查：

```bash
if [ -f "$outdir/single_repr_model_1_pred_0.npy" ]; then
  skip
fi
```

也就是说，这里把“单任务是否完成”的判断标准设为：

- 已经成功导出了 `single representation`

这比只看 `ranked_0.pdb` 更贴近后续主流程需求，因为后面特征抽取真正依赖的是 `single_repr_*.npy`。

---

## 为什么它直接打开 `save_single_representation`

因为当前主流程已经不再只是结构预测，而是“结构预测 + 内部表示导出”的联合流程。

脚本在生成 runner 时直接加入：

- `--save_single_representation=true`
- `--run_alphafold_source_path=alphafold2/run_alphafold.py`

这说明它依赖的是你本地改过的 AlphaFold 入口，而不是完全原版 runner。

## 如何运行

### 先生成 full-run runner

```bash
python scripts/3.prepare_full_single_repr_run.py
```

### 再真正启动 full-run

```bash
bash results/af2/single-repr-full/run_single_repr_full.sh
```

### 显式指定参数

```bash
python scripts/3.prepare_full_single_repr_run.py \
  --input-manifest data/manifests/fireprotdb_phase1_af2_manifest.csv \
  --gpu-ids 0,1,2,3 \
  --data-dir /data/AFDB \
  --output-dir results/af2/single-repr-full/outputs \
  --log-dir results/af2/single-repr-full/logs \
  --runner-script results/af2/single-repr-full/run_single_repr_full.sh \
  --summary-json results/af2/single-repr-full/summary.json
```

---

## 运行前后要检查什么

### 运行前

检查：

1. `summary.json` 里的 `total_tasks` 是否合理
2. `gpu_ids` 是否真的是 4 张卡
3. `run_script` 与 `run_alphafold_source_path` 是否指向当前仓库版本

### 运行后

检查：

1. `outputs/<target>/single_repr_model_1_pred_0.npy` 是否逐步出现
2. `logs/*.log` 是否正常滚动
3. 是否存在长时间卡在某个超长蛋白的情况

## 常见坑

### 1. 这个脚本不会自动启动 full-run

它只是“准备”运行脚本，不是“执行”脚本。

### 2. GPU 数量被硬编码成 4 卡约束

如果你不是 4 卡环境，当前脚本会直接报错。

### 3. 依赖本地修改版 `run_alphafold.py`

如果那个文件被替换或回退，single representation 可能导不出来。

### 4. skip 标准依赖 `.npy`

如果输出目录里只有 PDB、没有 `single_repr_model_1_pred_0.npy`，脚本仍会视为未完成。
