# 2.build_mutant_fastas.py

## Role in the pipeline

This script takes the cleaned phase-1 mutation table and converts it into the actual sequence assets required by the AlphaFold stage:

1. WT FASTA files
2. mutant FASTA files

It also creates the full AF2 manifest, which becomes the central index used by AF2 execution, representation extraction, and MLP training.

---

## What this script is for

The output of the previous step, `fireprotdb_phase1_ddg_clean.csv`, is still just a structured table.

AlphaFold does not consume that table directly. It needs:

- one FASTA per sequence target
- a manifest tying sample identity, protein identity, ddG label, and FASTA paths together

This script is therefore the bridge between the cleaned dataset and the inference-ready assets.

---

## Inputs and outputs

### Input

- default input: `data/processed/fireprotdb_phase1_ddg_clean.csv`

### Outputs

- WT FASTA directory: `data/interim/fasta/wild_type/`
- mutant FASTA directory: `data/interim/fasta/mutant/`
- manifest CSV: `data/manifests/fireprotdb_phase1_af2_manifest.csv`
- summary JSON: `data/manifests/fireprotdb_phase1_af2_manifest_summary.json`

---

## How the code is organized

The script follows a helper-first structure.

### 1. Top-level version marker

- `VERSION = '1.0.0'`

Used for provenance in the summary output.

### 2. Helper functions

- `wrap_fasta_sequence()`
  - wraps long sequences into FASTA-friendly line widths
- `write_fasta()`
  - writes a single FASTA file
- `resolve_repo_path()`
  - resolves relative paths from the repository root
- `load_clean_rows()`
  - loads the cleaned phase-1 CSV
- `build_manifest_rows()`
  - the main transformation function; generates FASTAs and manifest rows
- `write_csv_rows()`
  - writes the manifest CSV
- `write_summary()`
  - writes the summary JSON
- `build_summary()`
  - constructs the summary payload

### 3. `main()`

`main()` only orchestrates the workflow:

1. resolve paths
2. load clean rows
3. generate FASTAs and manifest rows
4. write the manifest
5. write the summary

This keeps the execution path short and explicit.

---

## How FASTA generation works

### WT FASTA generation

For each unique `protein_id`, the script writes exactly one WT FASTA:

- filename: `{protein_id}.fasta`
- FASTA header: `>{protein_id}`

This avoids writing duplicate WT sequences for every mutation sample.

### Mutant FASTA generation

For each mutation sample, the script writes one mutant FASTA:

- filename: `{protein_id}__{mutation_label}.fasta`
- FASTA header: `>{mutation_id}`

So mutant files are expanded one-to-one with samples.

---

## What the manifest stores

The generated `fireprotdb_phase1_af2_manifest.csv` is the central coordination table of the workflow.

It records at least:

- `sample_index`
- `sample_id`
- `protein_id`
- `mutation_label`
- `position`
- `wild_type`
- `mutation`
- `median_ddg`
- `num_experiments`
- `sequence_length`
- `wt_fasta_path`
- `mutant_fasta_path`
- `wt_sequence`
- `mutant_sequence`

Later stages rely on this table for sample tracking and label alignment.

---

## Why this manifest matters

The manifest is not just a path table. It defines the stable sample identity used by the rest of the project.

For example:

- AF2 output directories are keyed by `protein_id` or `sample_id`
- feature extraction needs both `protein_id` and `sample_id` to locate WT and mutant representations
- training needs `sample_id` aligned with `ddG`

If this layer is inconsistent, the downstream pipeline becomes fragile.

## What to inspect after running

You should at least verify:

1. WT FASTAs exist
2. mutant FASTAs exist
3. the AF2 manifest exists
4. the summary statistics look sensible:
   - `unique_wt_fastas`
   - `unique_mutant_fastas`
   - `manifest_rows`

These values quickly reveal whether the sample expansion behaved as expected.

## Common pitfalls

### 1. Do not duplicate WT FASTAs per sample

The current behavior is correct: one WT FASTA per `protein_id`.

### 2. Path resolution assumes repository-root execution

The script resolves paths via `Path.cwd()`, so it should be run from the repository root.

### 3. `sample_id` is the true mutation-sample key

Downstream logic should rely on `sample_id`, not only on `mutation_label`.

### 4. This script assumes the upstream clean CSV is valid

It does not re-check mutation correctness. If the previous stage is wrong, the problem propagates.
