# 5.train_ddg_mlp.py

## Role in the pipeline

This is the final script in the current AF2stab mainline workflow. It consumes the 1152-dimensional features generated by `4.extract_single_repr_features.py` and trains/evaluates an MLP for ddG prediction.

It can be used both for simple fitting and for quantitative evaluation through holdout and K-fold CV.

---

## What this script does

Given an NPZ file containing:

- `X`: feature matrix of shape `(N, 1152)`
- `y`: ddG labels of shape `(N,)`
- `sample_ids`

the script will:

1. construct the MLP
2. train the model
3. compute regression metrics
4. save model weights and a summary JSON

---

## Model architecture

The `DdGMlp` network is:

- `1152 -> 1152`
- `ReLU`
- `1152 -> 512`
- `ReLU`
- `512 -> 512`
- `ReLU`
- `512 -> 1`

This matches the basic MLP design currently used in the project and is aligned with the intended paper-style baseline.

---

## How the code is organized

### 1. Top-level version and model definition

- `VERSION`
- `DdGMlp`

The model is defined at the top so it can be swapped easily later if needed.

### 2. Training and metric helpers

- `compute_regression_metrics()`
  - computes `mae / mse / rmse / pearson`
- `require_metric()`
  - enforces that a metric is not `None`
- `train_epoch()`
  - one training epoch
- `predict()`
  - batched inference plus evaluation loss
- `build_loader()`
  - standard DataLoader construction

### 3. Split helpers

- `shuffled_indices()`
- `split_train_val_indices()`
  - used for holdout evaluation
- `build_kfold_indices()`
  - used for CV mode

### 4. I/O helpers

- `resolve_repo_path()`
- `load_feature_dataset()`
- `write_summary()`

### 5. `main()`

`main()` is the top-level orchestrator:

1. read NPZ features
2. validate shapes
3. choose device and build the model
4. dispatch to the selected run mode
5. save the model state dict
6. write the summary JSON

---

## Supported run modes

The script supports:

- `--mode train_only`
- `--mode holdout`
- `--mode cv`

### 1. `train_only`

Fits the model on the entire provided dataset without an external validation split.

Good for:

- checking that optimization works
- observing training loss behavior

Not suitable for:

- reporting generalization performance

### 2. `holdout`

Runs one random train/validation split.

Relevant arguments:

- `--val-fraction`
- `--seed`

Good for:

- a quick validation estimate

### 3. `cv`

Runs K-fold cross-validation.

Relevant arguments:

- `--num-folds`
- `--seed`

Good for:

- a more stable baseline evaluation

---

## Behavior on tiny datasets

If the dataset has fewer than 2 samples, the script does not pretend to perform meaningful training. Instead, it enters:

- `smoketest_minimal_train_step`

This mode validates only:

- forward pass
- loss computation
- backward pass
- parameter update

This keeps the summary meaningful even for degenerate test inputs.

---

## What metrics are computed

The script reports:

- `MAE`
- `MSE`
- `RMSE`
- `Pearson`

Pearson is only returned when:

- there are at least 2 samples
- `y_true` has non-zero variance
- `y_pred` has non-zero variance

Otherwise it is set to `None`.

---

## Why sample IDs are no longer included by default

Earlier summaries wrote thousands of sample IDs into every JSON file. That made the summaries:

- much larger than necessary
- harder to compare across experiments
- harder to read because the important metrics were buried

The current default is therefore:

- **write only statistics and metrics**

If full sample lists are needed, you can enable:

- `--include-sample-ids`

## How to run it

### 1. Train only

```bash
python scripts/5.train_ddg_mlp.py \
  --input-npz data/processed/single_repr_features_full_partial.npz \
  --mode train_only \
  --summary-json results/models/ddg_mlp_full_partial_train_only_summary.json \
  --state-dict results/models/ddg_mlp_full_partial_train_only_state_dict.pt
```

### 2. Holdout evaluation

```bash
python scripts/5.train_ddg_mlp.py \
  --input-npz data/processed/single_repr_features_full_partial.npz \
  --mode holdout \
  --val-fraction 0.2 \
  --seed 42 \
  --summary-json results/models/ddg_mlp_full_partial_holdout_summary.json \
  --state-dict results/models/ddg_mlp_full_partial_holdout_state_dict.pt
```

### 3. 10-fold CV

```bash
python scripts/5.train_ddg_mlp.py \
  --input-npz data/processed/single_repr_features_full_partial.npz \
  --mode cv \
  --num-folds 10 \
  --seed 42 \
  --summary-json results/models/ddg_mlp_full_partial_cv10_summary.json \
  --state-dict results/models/ddg_mlp_full_partial_cv10_state_dict.pt
```

### 4. Include sample IDs explicitly

```bash
python scripts/5.train_ddg_mlp.py \
  --input-npz data/processed/single_repr_features_full_partial.npz \
  --mode holdout \
  --include-sample-ids
```

## What the outputs contain

### `state_dict`

Stores PyTorch model parameters for later reuse or inference.

### `summary_json`

Stores:

- dataset size
- feature dimensionality
- training hyperparameters
- selected mode
- losses
- regression metrics
- in CV mode, per-fold details plus aggregate statistics

---

## How to interpret the results

### `train_only`

Focus on:

- `final_loss`
- `min_loss`

This tells you whether the model can fit the provided data, not whether it generalizes.

### `holdout`

Focus on:

- `train_metrics`
- `val_metrics`

If training performance is excellent while validation is much worse, overfitting is likely strong.

### `cv`

Focus on:

- `aggregate_metrics`
- `folds`

This is the most useful result level for experiment comparison at the current stage.

---

## Common pitfalls

### 1. Default input paths still reflect an earlier smoketest-oriented setup

In the main pipeline, it is best to pass `--input-npz` explicitly.

### 2. `train_only` is not a generalization metric

It should not be compared directly to the paper result.

### 3. Current CV uses random splits

It is a useful engineering baseline, but not yet the stricter residue-based or homology-aware protocol from the paper.

### 4. The CV mode does not archive one state dict per fold

The main value of CV mode is the summary metrics, not per-fold checkpoint management.
