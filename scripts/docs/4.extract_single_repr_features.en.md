# 4.extract_single_repr_features.py

## Role in the pipeline

This script converts AlphaFold WT/mutant `single representation` outputs into the **1152-dimensional residue-level feature vectors** used by the ddG prediction model.

It is the layer that turns structure-generation artifacts into machine-learning inputs.

---

## What problem it solves

Although AlphaFold outputs `single_repr_model_*.npy`, the training step does not use those files directly. It needs:

- the 384-dimensional WT vector at the mutation site
- the 384-dimensional mutant vector at the mutation site
- the 384-dimensional difference vector

These three parts are concatenated into:

- `384 + 384 + 384 = 1152`

This script implements exactly that transformation.

---

## Inputs and outputs

### Inputs

- a manifest describing sample identity, mutation site, protein ID, and ddG label
- a representation output directory containing WT and mutant `.npy` files

The current default paths still reflect an earlier smoketest-style setup, so for the mainline pipeline it is best to pass arguments explicitly.

### Outputs

- `output_csv`
  - one metadata row per successfully extracted sample
- `output_npz`
  - the actual ML dataset containing `X`, `y`, and `sample_ids`
- `summary_json`
  - extraction counts, missing-file counts, and missing examples

---

## How the code is organized

### 1. Top-level constants

- `VERSION`
- `OUTPUT_FIELDNAMES`

`OUTPUT_FIELDNAMES` ensures the metadata CSV has a stable schema even when extraction is partial or empty.

### 2. Helper functions

- `resolve_repo_path()`
  - resolves paths relative to the repository root
- `load_manifest_rows()`
  - reads the manifest table
- `write_summary()`
  - writes the summary JSON

### 3. `main()`

`main()` performs the core workflow:

1. load the manifest
2. locate WT and mutant representation files for each sample
3. count and classify missing files
4. load the available `.npy` matrices
5. slice the mutation-site vectors
6. concatenate them into 1152-dim features
7. write CSV, NPZ, and summary outputs

---

## How the feature vector is computed

### Step 1: resolve WT and mutant representation paths

- WT path: `repr_output_dir / protein_id / single_repr_<model>.npy`
- mutant path: `repr_output_dir / sample_id / single_repr_<model>.npy`

### Step 2: convert the mutation position from 1-based to 0-based

```python
residue_index = position - 1
```

### Step 3: extract residue-level vectors

- `wt_vec = wt_repr[residue_index]`
- `mut_vec = mut_repr[residue_index]`
- `diff_vec = mut_vec - wt_vec`

### Step 4: concatenate

```python
feature_vec = np.concatenate([wt_vec, mut_vec, diff_vec], axis=0)
```

The script enforces:

- `feature_vec.shape == (1152,)`

If that invariant is violated, it raises an error immediately.

---

## Why partial / incremental extraction is supported

The full AF2 run may take a long time, and it is often useful to begin downstream processing before every target has finished.

To support that workflow, the script behaves as follows by default:

- missing WT or mutant files are counted and skipped
- the extraction run continues for the samples that are already complete

This makes it possible to generate training-ready partial datasets while AF2 is still running.

---

## What strict mode does

Relevant flag:

- `--strict-missing`

Default behavior:

- missing files -> count and skip

Strict behavior:

- missing files -> raise `FileNotFoundError`

This is useful when:

1. you believe the full run should already be complete and want a hard completeness check
2. you are generating the final production feature dataset and do not want partial semantics

## How to run it

### Recommended partial extraction on the full run

```bash
python scripts/4.extract_single_repr_features.py \
  --input-manifest data/manifests/fireprotdb_phase1_af2_manifest.csv \
  --repr-output-dir results/af2/single-repr-full/outputs \
  --output-csv data/processed/single_repr_features_full_partial.csv \
  --output-npz data/processed/single_repr_features_full_partial.npz \
  --summary-json data/processed/single_repr_features_full_partial_summary.json
```

### Final strict extraction

```bash
python scripts/4.extract_single_repr_features.py \
  --input-manifest data/manifests/fireprotdb_phase1_af2_manifest.csv \
  --repr-output-dir results/af2/single-repr-full/outputs \
  --output-csv data/processed/single_repr_features_full.csv \
  --output-npz data/processed/single_repr_features_full.npz \
  --summary-json data/processed/single_repr_features_full_summary.json \
  --strict-missing
```

## What to inspect after running

The most important fields are:

1. `rows_extracted`
2. `rows_missing_any`
3. `rows_missing_mut_only`
4. `feature_matrix_shape`

If `rows_missing_mut_only` is high, that usually means WT representations are mostly ready while many mutant runs are still incomplete.

## Common pitfalls

### 1. The default CLI values are old-style

The defaults still reflect an earlier smoketest-oriented setup, so for the main pipeline you should pass `--input-manifest` and `--repr-output-dir` explicitly.

### 2. Mutation-site indexing must be handled carefully

The manifest is 1-based, Python arrays are 0-based.

### 3. Presence of a `.npy` file does not imply multi-model completeness

The script looks for one model-specific representation file at a time.

### 4. These are residue-level features, not sequence-level features

The script extracts a single residue vector rather than preserving the full `(N_res, 384)` matrix for training.
